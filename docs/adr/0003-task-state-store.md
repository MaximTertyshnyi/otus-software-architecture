# 0003 · Хранилище состояния задач: клиент сейчас, сервер потом

- **Статус:** proposed
- **Дата:** 2026-07-17
- **Ответственные:** —
- **Связанные ASR:** ASR-1 (устойчивость), ASR-7 (эволюционируемость)

## Контекст и постановка проблемы

Состояние активных задач надо где-то хранить, чтобы пережить reload. Сейчас это
localStorage с контрактом-пустышкой (`rtRecord({})`) — то есть **без валидации
схемы**: битая запись переживёт перезагрузку и может сломать восстановление.
Нужно решить, где хранить состояние и как оставить путь к серверному job-store,
не имея сейчас доступа к бэкенду (C-1).

## Драйверы решения

- Задачи должны восстанавливаться после reload (ASR-1).
- Битые/устаревшие записи не должны ломать старт (валидация).
- Позже хранилище нужно заменить серверным без переписывания консьюмеров (ASR-7).
- Серверную часть менять нельзя сейчас (C-1).

## Рассмотренные варианты

- **A. `Persistence port` + адаптер localStorage с валидацией схемы (Runtypes).**
  Домен работает с портом; при чтении невалидные записи отбрасываются. Серверный
  адаптер — будущая реализация того же порта.
- **B. Прямой localStorage без порта (как сейчас).** Просто, но привязывает домен к
  браузерному хранилищу и не даёт пути к серверу.
- **C. Сразу серверный store.** Идеально для надёжности, но вне границ (C-1).

## Решение

Выбран **вариант A**: интерфейс `Persistence port`, за которым сейчас стоит
валидируемый localStorage-адаптер, а в будущем — серверный job-store.

### Последствия

- ✅ Восстановление после reload + защита от битых записей (валидация на чтении).
- ✅ Явный, дешёвый путь миграции на сервер: новая реализация порта, домен не трогаем.
- ⚠️ localStorage остаётся per-device и ограничен по объёму — принимаем как
  осознанное ограничение клиентского этапа.
- 🔒 Контракт порта (`save/load/remove` + модель задачи) фиксируется как граница —
  именно он определит стоимость серверной миграции.

## Плюсы и минусы вариантов

### A — порт + валидируемый localStorage
- ✅ Изоляция хранилища; путь к серверу; безопасное чтение.
- ❌ Небольшой оверхед абстракции; localStorage-ограничения остаются.

### B — прямой localStorage
- ✅ Минимум кода.
- ❌ Нет валидации, нет пути к серверу — консервирует текущую боль.

### C — сразу сервер
- ✅ Надёжность из коробки.
- ❌ Невозможно сейчас (C-1).

## Дополнительно

Эволюция «клиент → серверный job-сервис» — это и есть заявленный в проекте переход
«монолит → сервис». Здесь он зафиксирован решением, а не реализуется в коде.
