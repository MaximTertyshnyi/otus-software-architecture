# 0005 · Модель рендеринга и сборки: CSR + code splitting

- **Статус:** proposed
- **Дата:** 2026-08-12
- **Ответственные:** —
- **Связанные ASR:** ASR-3 (изменяемость); атрибут Performance (второстепенный, см. [03-quality-attributes](../03-quality-attributes.md))

## Контекст и постановка проблемы

Нужно выбрать, как модуль рендерится и собирается. Соблазн — взять «модно» (SSR/SSG),
но модуль показывается после авторизации, данные приватные и постоянно меняются (статус
задачи обновляется каждые секунды), а сам Selene — клиентское SPA. Вопрос: даёт ли SSR
что-то по метрикам, или наш реальный рычаг в другом.

## Драйверы решения

- LCP/TTFB первого экрана определяет оболочка Selene, а не наш модуль.
- Контент персональный и живой — кэшировать отрендеренный HTML на CDN нечего.
- Добавление нового типа задачи не должно раздувать начальный бандл (ASR-3).

## Рассмотренные варианты

**A. CSR + code splitting.** Рендерим на клиенте, тяжёлое (типы задач, рендеры результата,
транспорты) грузим динамическим импортом. В CI — бюджет бандла.

**B. SSR.** Сервер отдаёт готовый HTML модуля, дальше гидратация.

**C. SSG.** Пререндер на билде.

## Решение

Берём вариант A. Раз TTFB/LCP держит хост, а контент приватный и динамичный, SSR/SSG не
улучшают ключевые метрики, зато добавляют серверный рантайм и гидратацию. Наш измеримый
рычаг — вес и момент загрузки JS, поэтому вкладываемся в code splitting, а не в рендеринг.

### Последствия

- Меньше инфраструктуры: не нужен SSR-сервер и возня с гидратацией приватного контента.
- Начальный бандл модуля маленький; новый тип задачи приезжает своим чанком по требованию.
- INP/TTI зависят от нашего JS — за этим следим бюджетом бандла в CI, иначе выигрыш утечёт.
- Первый показ самого модуля — после загрузки его чанка; для пост-авторного виджета это
  приемлемо, но если появится публичный SEO-экран, решение придётся пересмотреть.

## Плюсы и минусы вариантов

**A — CSR + splitting.** Простая доставка, контроль веса JS, прямая связь с изменяемостью.
Взамен — сами следим за размером бандла и за тем, чтобы ленивая загрузка не била по UX.

**B — SSR.** Лучше для публичного контентного первого экрана, но у нас его нет: платим
сервером и гидратацией без выигрыша в LCP.

**C — SSG.** Хорош для статики; наши данные динамические и приватные — не подходит.
