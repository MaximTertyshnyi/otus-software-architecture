# 0001 · Гарантии доставки задачи на клиенте

- **Статус:** proposed
- **Дата:** 2026-07-17
- **Ответственные:** —
- **Связанные ASR:** ASR-2 (гарантированное завершение), ASR-5 (корректность повторов)

## Контекст и постановка проблемы

Задача живёт на ненадёжном клиенте: вкладку могут закрыть, перезагрузить, сеть —
оборваться. Нужно определить, какую гарантию выполнения даёт платформа и как это
согласуется с деньгами/UX (повторная генерация не должна плодить дубликаты).

Сейчас: очередь переживает reload (localStorage) и повторно шлёт все in-flight
запросы при старте — то есть де-факто уже **at-least-once**, но без явной
идемпотентности; дубликаты возможны.

## Драйверы решения

- Задача не должна теряться при reload/краше (ASR-1).
- Повторы не должны создавать дубликат результата (ASR-5).
- Серверную часть менять нельзя (C-1) — гарантию строим поверх существующего API.

## Рассмотренные варианты

- **A. at-least-once + идемпотентность по `job-id` на клиенте.** При старте
  переигрываем незавершённые задачи; дубликаты гасим тем, что `job-id` = ключ,
  и повторный `done` для уже завершённой задачи игнорируется.
- **B. at-most-once.** Не переигрываем после reload — задача просто теряется.
  Проще, но нарушает ASR-1/ASR-2.
- **C. exactly-once.** Требует серверной координации/дедупа → вне границ (C-1).

## Решение

Выбран **вариант A (at-least-once + идемпотентность по `job-id`)**, потому что это
максимум гарантии, достижимый без изменения бэкенда, и он закрывает ASR-1/ASR-2/ASR-5.

### Последствия

- ✅ Задачи переживают reload и доводятся до терминального состояния.
- ✅ Повторы безопасны: результат дедуплицируется по `job-id`.
- ⚠️ Возможны лишние повторные запросы (цена at-least-once) — смягчается backoff/dedup.
- 🔒 `job-id` становится частью контракта задачи и ключом идемпотентности —
  менять его модель потом дорого.

## Плюсы и минусы вариантов

### A — at-least-once + идемпотентность
- ✅ Устойчивость без бэкенда; закрывает ключевые ASR.
- ❌ Возможны повторные вызовы; идемпотентность надо честно реализовать и протестировать.

### B — at-most-once
- ✅ Простейшая реализация.
- ❌ Теряет задачи при reload — прямое нарушение ASR-1/ASR-2.

### C — exactly-once
- ✅ Идеальная семантика.
- ❌ Невозможно без серверной координации (C-1).
