# 03 · Атрибуты качества, trade-offs и сценарии

## Зачем нужны атрибуты качества

Функциональные требования говорят, что система делает. Атрибуты качества говорят,
насколько хорошо она это делает: устойчиво, изменяемо, надёжно. Именно они и формируют
архитектуру — почти каждое решение усиливает одни свойства за счёт других. Без названных
атрибутов «хорошая архитектура» — пустая фраза: хорошая для чего? Когда атрибуты названы,
качество можно обсуждать и проверять сценариями, а не спорить о вкусах.

## Каталог атрибутов

Свойства, проявляющиеся во время работы:

| Атрибут | Кратко | Роль в теме |
|---|---|---|
| Availability / Resilience | переживает сбои и восстанавливается | приоритет |
| Reliability | корректный результат, без дублей и потерь | приоритет |
| Performance | латентность и пропускная способность | второстепенно |
| Scalability | поведение под ростом нагрузки | вне фокуса |
| Security | доступ и целостность | закрыто платформой |
| Observability | видимость состояния и переходов | поддерживает |
| Usability | предсказуемость для пользователя | поддерживает |

Свойства, проявляющиеся при изменении и сопровождении:

| Атрибут | Кратко | Роль в теме |
|---|---|---|
| Modifiability | стоимость изменения и добавления фич | приоритет |
| Testability | лёгкость проверки поведения | поддерживает |
| Deployability | простота выката | вне фокуса |
| Reusability | переиспользуемость компонентов | поддерживает |

## Trade-offs

Атрибуты тянут в разные стороны: усиливая один, платишь другим. Ключевые компромиссы темы:

| Компромисс | Что выбираем | Чем платим | Где зафиксировано |
|---|---|---|---|
| устойчивость против простоты | восстановление задач и персистентность | больше кода и состояния | [ADR-0003](adr/0003-task-state-store.md) |
| at-least-once против дублей | гарантию «хотя бы раз» | обязательную идемпотентность по job-id | [ADR-0001](adr/0001-delivery-guarantees.md) |
| изменяемость против простоты | порты и адаптеры | косвенность и риск «дырявой» абстракции | [ADR-0002](adr/0002-transport-port.md) |
| единый транспорт против точной модели push/pull | один контракт для poll и WS | нормализацию двух разных потоков | [ADR-0002](adr/0002-transport-port.md) |
| наблюдаемость против шума | единый лог переходов | объём логов | ASR-6 |

Часть свойств сознательно не в фокусе: производительность (задачи и так длятся секунды-минуты,
задержка опроса вторична), безопасность (авторизацию уже держит платформа) и масштабируемость
(нагрузка ограничена одним пользователем).

## Приоритетные атрибуты темы

Архитектура строится вокруг трёх свойств; остальные — поддерживающие.

**Устойчивость.** Задача переживает перезагрузку и сбой вкладки. Это приоритет номер один,
потому что за долгую AI-генерацию пользователь фактически платит ожиданием, и потерять
запущенную задачу — значит потерять и результат, и доверие. Закрывает ASR-1 и ASR-2.

**Изменяемость.** Новый тип задачи подключается без дублирования стейт-машины. Сегодня
каждый тип — это около 490 строк почти одинакового кода; это и есть главная боль
сопровождения, которую тема снимает. Закрывает ASR-3.

**Надёжность.** Повтор не плодит дубликаты, и каждая задача доходит до терминального
состояния. Без идемпотентности at-least-once даёт задвоенные результаты, а тихий дроп по
таймауту оставляет пользователя с вечным спиннером. Закрывает ASR-5 и часть ASR-2.

## Сценарии качества

Формат из шести частей: источник, стимул, артефакт, среда, отклик и мера отклика. Именно
мера превращает пожелание в проверяемое требование.

### QAS-1 · Устойчивость

| Часть | Значение |
|---|---|
| Источник | пользователь или среда браузера |
| Стимул | перезагрузка вкладки во время активной AI-задачи |
| Артефакт | Task Orchestrator и Persistence port |
| Среда | нормальная работа, задача в статусе `processing` |
| Отклик | после рестарта платформа поднимает задачу из хранилища и продолжает опрос или подписку. В норме приходит `done` за секунды. Если бэкенд молчит, задача не теряется, а по достижении защитного таймаута уходит в `timeout` с понятным исходом |
| Мера отклика | восстановлены все активные задачи; в норме терминал за секунды; при деградации — не позже клиентского таймаута и всегда с явным терминальным состоянием, без тихого дропа; дубликатов результата ноль |

Про таймауты: 7 минут для генерации и 180 секунд для чата — это защитные пороги на случай,
когда что-то пошло не так, а не ожидаемая длительность; в норме задача завершается заметно
быстрее. Смысл темы как раз в том, что сегодня по достижении потолка задача молча пропадает,
а должна переходить в явный `timeout` с понятной пользователю реакцией.

### QAS-2 · Изменяемость

| Часть | Значение |
|---|---|
| Источник | разработчик |
| Стимул | нужно добавить новый тип AI-задачи |
| Артефакт | конфиг задачи и контракт ответа |
| Среда | время разработки |
| Отклик | тип подключается через `createAsyncAiTask`, стейт-машина не меняется |
| Мера отклика | нового кода порядка 60 строк; дублирования стейт-машины нет; существующие типы задач не затронуты |

Итог: приоритетные атрибуты — устойчивость, изменяемость и надёжность; опорный сценарий
защиты — QAS-1, с измеримой мерой отклика.
