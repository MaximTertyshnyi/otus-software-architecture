# 01 · Контекст и границы

## Задача

Результат AI-генерации в продукте ждут сразу несколькими путями. Генерация «групп»
на карте и генерация AI-блоков работают на long-polling — и это две почти одинаковые
стейт-машины примерно по 490 строк каждая, обе поверх общей очереди `polling_queue`.
Чат с ассистентом устроен совсем иначе, на WebSocket через Centrifugo. Единой модели
асинхронной задачи между ними нет: одно и то же по смыслу «дождаться ответа» написано
три раза и тремя способами.

Проект проектирует такую общую модель — платформу оркестрации задач с гарантиями
доставки, сменным транспортом и явными терминальными состояниями.

## Границы

Проектируем и показываем:

- job-модель и стейт-машину задачи;
- планировщик опроса с настраиваемыми backoff и jitter;
- `Transport port` с адаптерами long-poll и WebSocket;
- `Persistence port` с адаптером localStorage и валидацией схемы;
- прогресс и терминальные состояния.

Серверный job-store, серверный планировщик и exactly-once оставляем как направление
развития — оно описано в [ADR-0003](adr/0003-task-state-store.md), а не строится здесь.

## Внешние зависимости

| Актор / система | Роль |
|---|---|
| Пользователь | инициирует AI-задачи, ждёт результат |
| Backend генерации (группы, блоки) | старт задачи `POST …/collect`, затем опрос статуса `GET <uri>` |
| Centrifugo | WebSocket pub/sub для чата |
| localStorage браузера | хранит состояние активных задач между перезагрузками |

## Глоссарий

| Термин | Значение |
|---|---|
| **Задача (job)** | единица асинхронной работы с уникальным `job-id` и жизненным циклом |
| **Транспорт** | способ получить результат: long-poll (опрос) или ws-push (подписка) |
| **Терминальное состояние** | `done`, `failed`, `timeout` или `canceled` — состояние, из которого нет переходов |
| **Клиентский таймаут** | защитный порог на случай, когда что-то пошло не так: 7 мин для генерации (`POLLING_UPPER_LIMIT`), 180 с для чата (`fallback_config.timeout_seconds`). Это не ожидаемая длительность — в норме задача завершается кратно быстрее |
| **at-least-once** | гарантия, что задача выполнится хотя бы раз; из-за возможных повторов нужна идемпотентность |
| **Идемпотентность по job-id** | повторный запуск с тем же `job-id` не создаёт второй результат |
| **backoff / jitter** | нарастающий интервал между опросами и случайный разброс поверх него, чтобы избегать синхронных всплесков запросов |
