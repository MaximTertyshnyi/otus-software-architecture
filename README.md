# Async AI Task Orchestration Platform — архитектурная документация

Сквозной проект курса **OTUS Software Architecture**.

Клиентская платформа оркестрации асинхронных AI-задач: единая job-модель с
гарантиями доставки и сменным транспортом (long-poll / WebSocket), заменяющая
две продублированные стейт-машины и разрозненные механизмы ожидания AI-ответа.

> Доменная основа — модуль TASS в монорепозитории Selene (Aviasales):
> `ai_group_query`, `create_ai_block_api`, `polling_queue`, чат на Centrifugo.
> Здесь — только архитектурная документация проекта, без продакшен-кода.

## Архитектурные драйверы

- **D1 · Изменяемость:** две long-poll стейт-машины примерно по 490 строк и отдельный
  WS-движок дублируют один жизненный цикл; новый тип задачи не должен требовать ещё
  одной копии.
- **D2 · Надёжное завершение:** задача должна пережить reload и сбой транспорта,
  прийти ровно в один терминал и не создать дубль результата.
- **D3 · Независимость от интеграций:** long-poll, WebSocket и будущие способы доставки
  меняются независимо от правил жизненного цикла задачи.

## Ценность

### Со стороны архитектуры

- **Единая job-модель вместо трёх механизмов.** Ожидание AI-ответа реализовано
  трижды (два дублирующих long-poll консьюмера + WS-чат) → сводится к одной
  абстракции `createAsyncAiTask`. Это про изменяемость, а не про фичи.
- **Ports & Adapters (гексагон).** Транспорт (poll/WS) и хранилище
  (localStorage/сервер) уходят за порты; доменная логика перестаёт зависеть от
  инфраструктуры → архитектура становится эволюционируемой (путь «клиент →
  серверный job-сервис» открывается заменой адаптера, без переписывания).
- **Явные границы и решения** зафиксированы в ADR — система переходит из «просто
  работает» в «управляемо развивается».

### Со стороны откликов (поведение под стимулом)

- **Устойчивость:** задача переживает reload/сбой вкладки и доводится до конца.
- **Гарантированное завершение:** молчаливый дроп по таймауту превращается в явный
  `timeout` с понятным исходом — нет «вечных спиннеров».
- **Корректность повторов:** at-least-once + идемпотентность по `job-id` → повтор
  не плодит дубликаты результата.
- Отклики **измеримы** (см. [сценарии качества](docs/03-quality-attributes.md)):
  100% восстановления, терминал всегда наступает, дублей = 0.

### Со стороны улучшений фронта

- **−~930 строк дублирования:** два консьюмера по ~490 строк → два конфига по ~60.
  Новый тип AI-задачи = конфиг + контракт, а не копипаста стейт-машины.
- **Одно предсказуемое поведение** вместо расходящегося (сейчас один консьюмер
  дебаунсит запросы, другой нет; бэкофф/таймаут захардкожены).
- **Надёжная персистентность:** валидируемая схема вместо `rtRecord({})` — битая
  запись не ломает старт.
- **Чат в общей модели:** WebSocket становится ещё одним транспортом, развилка «два
  движка» исчезает.
